# 運用の型（段階・役割・相談）

- このフォルダは、運用の型（段階・役割・関わり方・相談の手続き）のひな形と道具です。型の版：<入れたときのスキルの版>（元は honeycomb-browser-grok の `docs/operating-kit/`）。<入れた日> に入れました。
- このリポジトリの決まりの正本は、CLAUDE.md と docs/main-agent.md です。このフォルダは写しの元なので、食い違うときは CLAUDE.md に従います。
- モデル名は書きません。ひな形では、モデルの入る所を〈小〉〈主〉〈上〉で書きます。このリポジトリでの当てはめは、CLAUDE.md の「役割」の表です。
- スキル `operating-kit` があるセッションでは、次の段階の一言を出す・決まりのずれを点検する、ができます（ユーザー全体のスキルなら `/operating-kit`、プラグインで入れたなら `/operating-kit:operating-kit`）。

## 1. 何のための型か

一人の判断役（主担当）が、下調べ・整備・考察と発想・計画とデザイン・実装を段階ごとに新しいセッションで進め、要所だけで上位のモデルに相談する、そのための決まりの組み立てです。ねらいは三つです。判断がぶれないこと（判断は一人、票では決めない）。使う人が舵を握ること（モデルの切り替え・相談の許し・大きな決めごとは使う人）。セッションが替わっても続けられること（橋渡しは一つの再開用のメモ）。

## 2. 型の芯（変えない方がよい所）

1. **段階を分け、段階ごとにセッションを替える。** 橋渡しは HANDOFF.md 一つ。
2. **判断は一人。** 主担当だけが判定する。調査担当・検討担当・相談役・実装担当は、判断しない。
3. **相談は使う人の許しで。** 合図の語は、主担当が「相談しますか」と聞いた論点への返事か、論点を名指しした頼みのときだけ効く。説明・引用・否定の中の語では動かない。
4. **票で決めない。** 割れたら、両側の根拠（ファイルと行）を主担当が自分で読んで判定する。
5. **止まる目安は二つの掛け算。** 決めきれない案が二つ以上残る、かつ、選び違えると戻すのが重い。
6. **記録してから止まる。** 使う人の答えと、相談の結論を分けて、日付つきで書く。
7. **モデルと effort は使う人が切り替える。** 主担当は切り替えない。
8. **モデル名は一か所だけ**（CLAUDE.md）。
9. **広げる行程では絞らない。** 判定（箱分け）は、案の一覧を残してから主担当がする。

## 3. 部品（このフォルダ）

| ファイル | 中身 |
|---|---|
| `CLAUDE.template.md`・`main-agent.template.md`・`HANDOFF.template.md` | 決まり・主担当の進め方・再開用のメモのひな形（入れたときの元。今の決まりは CLAUDE.md・docs/main-agent.md・HANDOFF.md） |
| `spec.template.md` | 実装担当に渡す仕様のひな形（使うたびに `docs/wip/<日付>/specs/<名前>.md` へ写す） |
| `wip-index.template.md` | 段階①-1 の索引のひな形（使うたびに `docs/wip/<日付>/README.md` へ写す） |
| `prompts.md` | 段階ごとに新しいセッションへ貼る一言、移るときの言葉、合図の早見、ワークフローの渡し方 |
| `workflows/consult.js` | 一つの論点を、観点ごとに読み取り専用で相談するワークフロー（相談役・検討担当。まとまった案を点検する絞る用。広げさせる観点には主担当の見立てを見せない blind がある） |
| `workflows/ideate.js` | 段階②-1 で、観点ごとに案を広げ、照らし、疑うワークフロー（検討担当・調査担当。判定しない） |
| `workflows/survey.js` | 話題ごとに読んで集めるワークフロー（調査担当） |

ひな形の名前を `CLAUDE.md` にしていないのは、このフォルダの中で決まりとして読み込まれないようにするためです。

## 4. 新しいセッションの始め方

1. CLAUDE.md の段階の表のとおりに、セッションのモデルと合図の語を設定する（使う人が行う）。
2. このフォルダか作業枝で、新しいセッションを始める（別の枝だと HANDOFF.md が見えない）。
3. `prompts.md` の、その段階の一言を貼る。
4. 終わったら、そのセッションが「移ってよい」と提案する。使う人が決めて、次の段階のセッションを始める。

## 5. 〈〉の一覧（ひな形を読むときのため）

| 〈〉 | 入るもの |
|---|---|
| 〈小〉 | 調査担当・実装担当・段階①-1 のセッションのモデル |
| 〈主〉 | 主担当・検討担当・相談役（代わり）のモデル |
| 〈上〉 | 相談役（基本）と、関わり方 (A) の段階のセッションのモデル |
| 〈主の effort〉 | 段階③ のセッションの effort |
| 〈合図の語〉 | 相談の許しの語 |
| 〈名前〉・〈正本〉・〈作業枝〉・〈入れない枝〉 | リポジトリの名前、正本の repo、コミットしてよい枝、入れない枝 |
| 〈型検査〉 | 編集のあとに通す確かめのコマンド |
| 〈コードの場所〉・〈重い層〉 | 段階②-1・②-2 で変えない所、実装担当に触らせない所 |
| 〈決まりの文書〉・〈大きな決めごとの一覧〉・〈計画書の形〉 | 守ることの細目、止まって聞くもの、計画書の見出し |
| 〈見本の置き場〉・〈思いつきの置き場〉 | 画面の見本、判定の前の思いつき |

## 6. 直すとき

- CLAUDE.md や docs/main-agent.md の運用の決まりを変えたら、同じコミットで、このフォルダの対応するひな形も直す。
- 型そのもの（ほかのリポジトリにも効く直し）なら、元の honeycomb-browser-grok の `docs/operating-kit/` を直し、スキルにも写してもらう。
