# 〈名前〉（作業の決まり）

守ることの細目は 〈決まりの文書〉。主担当の進め方は docs/main-agent.md。今の状態と次の一手は HANDOFF.md。思いつきは 〈思いつきの置き場〉 に一行ずつ（判定の前。段階①-1 を除いて、だれでも書く）。判定のあとで計画に入れなかった案は 〈見送りの台帳〉 に（段階②-2 の主担当だけが書く。理由ともう一度見る条件つき）。

仕事は五つの段階（段階①-1〜段階③）に分けて進める。今どの段階かは HANDOFF.md の §0 の「今の段階」。文書どうしが食い違うときは、CLAUDE.md → docs/main-agent.md → 〈決まりの文書〉 の順に従う。

## 段階

モデル名は、CLAUDE.md の「段階」「役割」「関わり方」の節だけに書く。ほかの文書とコミットは、段階の名前と役割名で書く。丸数字の段階には必ず「段階」を付ける（ほかの番号とまぎれないように）。「段階②」とだけ書くときは、段階②-1 と ②-2 の両方を指す（片方だけなら「段階②-1」「段階②-2」と書く）。計画書の中の小分けは「段」と呼ぶ。

| 段階 | セッション（利用者が切り替える） | 目的 | できあがるもの | しないこと | ワークフローの中の役割とモデル |
|---|---|---|---|---|---|
| 段階①-1 下調べ | 〈小〉・〈合図の語〉（セッション全体） | 自由な考察・分析・発想・デザインの土台になる材料を集める | `docs/wip/<始めた日>/` の材料と索引 `README.md`（集めたもの・出どころ・確かめていないこと・段階①-2 への引き継ぎ） | wip の外に書く、決める・判定する、計画、コードを変える | 調査担当（〈小〉）だけ |
| 段階①-2 整備 | 〈主〉・〈合図の語〉（セッション全体） | 集めた材料で、自由に考察・分析・発想・デザインができるよう、文書と置き場を整える | 整えた文書と置き場、HANDOFF.md | 計画、段の分け方、案の採否を決める、コードを変える | 調査担当（〈小〉）、検討担当（〈主〉）、相談役（関わり方を選んだとき）。文書の機械的な直しは実装担当 |
| 段階②-1 考察と発想 | 〈主〉・〈合図の語〉（セッション全体）。関わり方 (A) のときは 〈上〉・〈合図の語〉 | 整えた材料と思いつきから、案を自由に、多くの観点から広げる（判定は段階②-2） | 案の一覧（`docs/wip/<②-1 を始めた日>/ideas/`。形は docs/operating-kit/ideas-index.template.md。全部の案と生の案、問い、改善の根、終わりの目安の照らし）、HANDOFF.md | 案の採否・箱分け・順位付け（判定は段階②-2）、計画、段の分け方、コードを変える | 調査担当（〈小〉。ideate.js の照らす相は 〈中〉）、検討担当（〈主〉）、相談役（関わり方 (B) を選んだとき）。(A) のときは相談役も 〈主〉 |
| 段階②-2 計画とデザイン | 〈主〉・〈合図の語〉（セッション全体）。関わり方 (A) のときは 〈上〉・〈合図の語〉 | 段階②-1 の案を判定し、計画とデザインを、おおまかに組む | 案の判定（箱と理由。案の一覧の判定の表に書き足す）、〈見送りの台帳〉 への書き足し（計画に入れなかった案）、計画書（〈計画書の形〉。段はおおまか）、画面の見本（〈見本の置き場〉）、大きな決めごとへの利用者の答え（HANDOFF.md の §4） | 実装（〈コードの場所〉を変えない）、段の細かい仕様、大きく広げ直す（要るなら段階②-1 へ戻ることを提案する） | 調査担当（〈小〉）、検討担当（〈主〉）、相談役（関わり方を選んだとき）。(A) のときは相談役も 〈主〉 |
| 段階③ 実装 | 〈主〉・effort は 〈主の effort〉（〈合図の語〉は入れない） | 計画を段ごとに作って確かめる | 段の仕様（`docs/wip/<日付>/specs/`）、コード、確かめ、文書の仕上げ、HANDOFF.md | 計画にない大きな決めごとを自分で決める、計画を作り直す（要るなら段階②-2 へ、広げ直しが要るなら段階②-1 へ戻ることを提案する） | 実装担当（〈小〉・Agent ツール）。ワークフローは利用者が 〈合図の語〉 と送った論点だけ：相談役（〈上〉、代わりは 〈主〉）、調査担当（〈小〉） |

- 段階ごとに新しいセッションを始める。橋渡しは HANDOFF.md（段階①-1 だけは wip の索引）。
- 段階②-1 と ②-2 は、利用者が決めたときだけ、一つのセッションでまとめてよい（HANDOFF.md の §0 には「段階②（②-1・②-2 をまとめる）」と書く。セッションは段階②-2 の行の設定。広げる周は段階②-1 の、判定の周からは段階②-2 の決まりに従う。docs/main-agent.md §2.6）。
- セッションのモデルと effort は利用者が切り替える。主担当は切り替えない（セッションのモデルや effort を変える道具も使わない）。
- 段階の外の仕事（決まりの直し、小さな直し）は、段階③ の設定で扱う。
- **始めるとき**：HANDOFF.md の §0 の「今の段階」（段階・関わり方・作業枝）と、セッションの設定（システムの文にあるモデル名、〈合図の語〉の知らせ）と、`git branch --show-current` を照らす。合わなければ、作業の前に利用者に伝える。
- **移るとき**：その段階のセッションが「移ってよい」と提案する（できたもの、確かめたこと・確かめていないこと、残り、次の段階の範囲、次の段階の関わり方の問い（おすすめ付き））。移る前に HANDOFF.md に引き継ぎを書き、作業枝にコミットし、`git fetch` してから push する。利用者が決めて、新しいセッションを始める。

## 段階①-1 の決まり（下調べのセッション）

段階①-1 のセッションは主担当ではない。この節と「作業の始め方」だけに従う。

1. 読んで集めるだけ。決めない、判定しない、計画しない、良し悪しを書かない。
2. 書くのは `docs/wip/<始めた日>/` の中だけ（その中の `ideas/`・`ideas-*/`・`specs/` には書かない）。ほかの文書・コード・HANDOFF.md は直さない。浮かんだ思いつきは、索引の「思いつき」の節に書く（判定しない）。
3. 集める範囲は、HANDOFF.md の §0 の「次の段階」に書いた範囲と、利用者の依頼。足りなければ聞く（三つまで）。
4. 一つの話題に一ファイル。事実には出どころ（ファイルと、見た時点の行）を付ける。確かめていないことは、そう書く。
5. 索引 `docs/wip/<始めた日>/README.md`（形は docs/operating-kit/wip-index.template.md）の終わりに「段階①-2 への引き継ぎ」を書く。段階①-2 の主担当が、最初にこれを HANDOFF.md の §0 へ写す。
6. ワークフローの agent() は、全部 `model: "〈小〉"` にする。一つのワークフローは 10 体以内。相談役と検討担当は呼ばない。ワークフローが使えなければ、ワークフローなしで集める。
7. 終わったら `git add docs/wip/<始めた日>/` だけをコミットし、`git fetch` してから作業枝に push する。ほかの git の操作はしない。「移ってよい」と提案して止まる。

## 役割（モデルとの対応は、この節と「段階」「関わり方」だけに書く）

| 役割 | Agent ツール・ワークフローでの指定 | 仕事 |

| 主担当 | 段階の表にある、そのセッションのモデル（関わり方 (A) の段階は 〈上〉）。`model` は指定しない。段階①-1 のセッションは主担当ではない | 計画・設計・判断・段階分け・難しい分析・統合・確かめ・利用者への説明 |
| 実装担当 | `subagent_type: "general-purpose"`、`model: "〈小〉"`。段階③ と、段階①-2 の文書の機械的な直し | 仕様が決まった小さな実装（大きさの目安は docs/main-agent.md §6） |
| 調査担当 | `model: "〈小〉"`（ワークフローの中だけ）。ideate.js の照らす相だけは `model: "〈中〉"`（ideate.js の lightModel） | 読み取りの下働き（ideate.js の照らす相も）。編集はしない |
| 検討担当 | `model: "〈主〉"`（段階①-2・②-1・②-2 のワークフローの中だけ） | 読み取り専用で、案を広げる・伸ばす・疑う。結論と根拠だけを返す。判定はしない |
| 相談役 | ワークフローの中だけ。基本は `model: "〈上〉"`、利用枠の制限などで使えないときの代わりは `model: "〈主〉"`。effort は "xhigh"。関わり方 (A) の段階では `model: "〈主〉"` | 段階③ では、利用者が 〈合図の語〉 と送った論点だけ。段階①-2・②-2 では関わり方 (B)(C) のとき、段階②-1 では (B) のとき。読み取り専用で相談し、結論と根拠だけを返させる |

- 主担当は、難しい分析・設計も自分で行う。止まって利用者に相談するのは、大きな決めごと（〈大きな決めごとの一覧〉）と、「相談の手続き」の止まる目安に当たるときだけ。
- 仕様が決まった小さな実装は実装担当に頼む。仕様は主担当が書く（形は docs/operating-kit/spec.template.md）。
- サブエージェントの結論は、主担当が確かめてから利用者に伝える。
- 相談・検討・実装には general-purpose を使う（Explore と Plan は CLAUDE.md を読まない）。

## 関わり方（段階①-2・②-1・②-2 で 〈上〉 がどう関わるか）

利用者が選ぶ。この節の外の記録（HANDOFF.md など）には、記号 (A)(B)(C)・なし で書く。選び方の目安と運び方は docs/main-agent.md §3。

| 記号 | 合図（会話で送る言葉） | 中身 |
|---|---|---|
| (A) 主 | 「〈上〉 主」 | その段階のセッションを 〈上〉・〈合図の語〉 にし、〈上〉 が主担当の仕事をする。その段階の相談役と検討担当は 〈主〉 |
| (B) 総合 | 「〈上〉 総合」 | 主担当が、まとまった案を丸ごと相談役に見てもらう（方向・抜け・別案など） |
| (C) 要所 | 「〈上〉 要所」 | 段階③ と同じく、迷う重要な論点だけを相談役に相談する |
| なし | 「〈上〉 なし」 | 相談役を使わない（調査担当と検討担当は使う） |

- **選ぶ時期**：前の段階の「移ってよい」の提案で、次の段階の関わり方を一つの問いで聞く（おすすめ付き）。答えは HANDOFF.md の §0 に書く。新しいセッションは、最初に記録と自分のモデルを照らし、記録が無ければ一つの問いで聞く。
  - 段階①-2 の「移ってよい」では、段階②-1 と ②-2 の関わり方をまとめて一つの問いで聞いてよい。§0 に両方を書き、段階②-1 の終わりでは聞き直さず、確かめるだけにする。
  - 選べるものが一つしか無いとき（〈上〉 が使えず (A)(B) を外したリポジトリの段階②-1 など）は、聞かずに なし と書く。
- **合図**：段階①-2・②-1・②-2 では、合図の言葉だけで変わる（段階②-1 では 要所 を使わない）。段階③ では 〈合図の語〉 と一緒に送る（使えるのは 要所 と 総合 だけ）。主 に変える・主 から外すときは、主担当が HANDOFF.md に書いてから、利用者にモデルの切り替えを頼む。
- **選んでいないとき**の既定：段階②-2 は (C) にし、段階②-2 を終える前に (B) を一回。段階①-2・②-1 は なし。
- **段階②-1 では (C) を使わない**：止まる目安の (b)（選び違えると戻すのが重い）に当たる決めが出ないため（案の一覧はコミットして残し、計画もコードも変えない）。段階②-1 で「〈上〉 要所」と送られたら、そのことを一行で伝え、(B) にするか、段階②-2 の関わり方として HANDOFF.md の §0 に書くかを、一つの問いで聞く。
- **許し**：(C) は論点ごとに止まって「相談しますか」と聞く（段階①-2・②-2 では返事は「はい」で足りる）。(B) は決めた時期に聞かずに行い、結果を知らせる。
- **(A) が利用枠で止まったとき**：利用者が 〈主〉・〈合図の語〉 の新しいセッションに切り替え、HANDOFF.md から続ける。(A) のセッションは区切りごとに HANDOFF.md へ書いてコミット・push する。
- **(A) で渡すもの**：セッション全体が 〈上〉 に渡る。このリポジトリの文書とコードだけを読む（リポジトリの外のフォルダ、環境変数、鍵は読まない）。
- どれを選んでも：相談役と検討担当の結論は決定ではない。判定は主担当がし、大きな決めごとは利用者が決める。相談に渡すのは、このリポジトリの文書とコードだけ。

## 〈合図の語〉（ワークフロー）

- **段階①-1・①-2・②-1・②-2**：〈合図の語〉 をセッション全体で入れる（利用者が設定する）。その既定（実質的な作業はワークフローで進める）に従う。ただし、下の「どの段階でも」と、「段階①-1 の決まり」「関わり方」を優先する。
- **段階③**：〈合図の語〉 は、利用者が依頼ごとに使う。ワークフローを起こすのは、利用者が 〈合図の語〉 と送った論点だけ。既定と、この節・「相談の手続き」・「役割」が食い違うときは、この節と「相談の手続き」を優先する。
- **どの段階でも**：
  - すべての agent() に model を明示する（省略すると今のセッションのモデルになる）。指定は「役割」の表のとおり。主担当が判断すべきものは、ワークフローに入れない。
  - ワークフローの中では編集させない。
  - 票や点数で決めない。
  - 一つのワークフローは 10 エージェント以内。
  - 結論は、通知の本文ではなく journal.jsonl の全文（体ごとの答え）を読んでから要約する。ideate.js の id を振った返す値は、通知が示す出力のファイルの JSON の result にある（生の案はそこから写す。docs/main-agent.md §2.2）。
  - ひな形のワークフローは docs/operating-kit/workflows/（`scriptPath` と `args` で渡す）。
- **見分け方**：利用者が 〈合図の語〉 と書いていない回にも知らせ（system-reminder）が出ていれば、セッション全体で入っている。「この回（this turn）」とあれば、その依頼だけ。

## 相談の手続き（段階③。段階①-2・②-2 の (C) にも使う）

段階①-2・②-2 の (C) では、1 の問いを「相談しますか」にし、返事は「はい」で足りる。4 の 3 と 5 は使わない。(B) の結論の読み方は、3 と 4 の 1〜2 に合わせる。

止まる目安は、次の両方に当たるとき：(a) 読む・型検査・小さな試しで決めきれない案が二つ以上残る。(b) 選び違えると戻すのが重い（〈重い層〉・保存の形・二つ以上の段・画面の作りにまたがる）。どちらかに当たらないものは、主担当が決め、理由を計画書の「決めごと」か HANDOFF.md の §4 に一行書く（段階②-2 の案の箱分けは、案の一覧の判定の表に書く）。

1. **止まる**：論点、迷っている理由、相談したいこと、案（おすすめは一つ）を書き、「〈合図の語〉 で相談しますか」と聞く。問いは、ほかに聞くことと合わせて三つまで。返事ごとの動き：
   - 〈合図の語〉 と送られたら、2 へ進む。承諾とみなすのは、主担当が聞いた論点への返事か、利用者が論点を名指しして頼んだときだけ。説明・引用・否定の中の語や、利用者が「説明の語」と断った語では、ワークフローを起こさず、そのことを一行で伝える。
   - 「いいえ」や「任せる」なら、主担当がおすすめで決め、理由と「相談なし」を HANDOFF.md の §4.2 に書いて進める。
   - 別の指示や案の選択なら、その指示に従い、利用者の答えとして HANDOFF.md の §4 に写す。
   - 返事を待つ。止まるときに、HANDOFF.md の §0 の 4 に「返事待ち」を一行書き、コミット・push しておく。返事が来たら消す。利用者が編集を止めている依頼の中では書かず、発言にだけ書く。
   - 〈合図の語〉 と送られないまま利用者が別の依頼をしたら、その論点は保留にして、依頼に従う。
2. **相談する**：その論点だけを、ワークフロー（docs/operating-kit/workflows/consult.js）で相談する。
   - 相談役（基本）に頼む。前から使えないと分かっているときは、最初から相談役（代わり）に頼む。
   - 基本が null を返したら、failures と journal.jsonl で理由を確かめる。利用枠・クレジットの制限と分かったときだけ、同じ指示文で代わりに頼み直す（新しい許しは要らない）。
   - agent() には `agentType: "general-purpose"` と effort `"xhigh"` を書く。指示文に、論点、読む文書、「読み取り専用。ファイルを書かない」、結論と根拠だけを返す形を入れる。
   - 相談に渡すのは、このリポジトリの文書とコードだけ。API キーや個人の情報は入れない。
   - 基本 5 体前後。頼み直しと合わせて 10 体以内。
3. **読む**：journal.jsonl の全文を読んでから、主担当が判定する。票では決めない。割れたら、両側の根拠を自分で読む。根拠にファイルと行の無い答えは使わない。使える答えが二つ未満なら、空と同じに扱う。
4. **確認を出す**：
   1. 先に記録する：HANDOFF.md の §4.2 に、日付、論点、答えた相談役（基本・代わり）と数、結論（三行まで）、主担当の判定と理由。
