# 主担当の進め方（主担当が読む文書）

- この文書は、段階①-2・段階②・段階③ の主担当向けです。段階①-1（下調べ）のセッションは、CLAUDE.md の「段階①-1 の決まり」だけに従います。
- 段階・役割・モデルの対応は CLAUDE.md だけにあります。この文書は、段階の名前と役割名で書きます。
- 守ることの細目は 〈決まりの文書〉。今の状態と次の一手は HANDOFF.md。食い違うときは、CLAUDE.md → この文書 → 〈決まりの文書〉 の順に従います。

## 1. 最初の 5 分

1. 状態を確かめる：`git branch --show-current`、`git status`、`git fetch`。
2. 読む：CLAUDE.md → HANDOFF.md の §0・§3・§4.2 → 〈決まりの文書〉 の守ること → 関係する計画書。全部は読まない。
3. 段階を照らす：HANDOFF.md の §0 の「今の段階」と、このセッションの設定（モデル名、〈合図の語〉 の知らせ）と、今の枝。合わなければ、作業の前に利用者に伝える。段階①-2 の最初は、wip の索引の「段階①-2 への引き継ぎ」を HANDOFF.md の §0 に写す。
4. 今の状態を 3 行で言い直す。食い違いがあれば、依頼に入る前に利用者に伝える。
5. 足りないことだけを聞く（多くても 3 つ）。調べて分かることは聞かない。

新しいセッションに貼る一言は docs/operating-kit/prompts.md。

## 2. 段階ごとの進め方

### 2.1 段階①-2（整備）
- 最初に、wip の索引の引き継ぎを HANDOFF.md の §0 に写す。関わり方を照らす（記録が無ければ一つの問いで聞く）。
- 材料を読み、自由に考察・分析・発想・デザインができるよう、文書と置き場を整える（索引、構造の地図の「今の状態」、思いつきの重なりをまとめる（判定はしない）、材料を置く場所）。
- 計画、段の分け方、案の採否は決めない。途中の思いつきは 〈思いつきの置き場〉 に一行。
- ワークフロー：調査担当で読み足し、検討担当に整え方の案を広げさせ、疑わせる。判定は主担当。

### 2.2 段階②（計画とデザイン）
- 計画書を 〈計画書の形〉 で書く。段はおおまかでよい（段階③ の始めに細かくする）。
- 画面が変わるなら、見本を 〈見本の置き場〉 に作る（〈コードの場所〉 は変えない）。
- 大きな決めごと（〈大きな決めごとの一覧〉）は、困ったこと・案・おすすめで聞き、答えを HANDOFF.md の §4 に写す。
- ワークフロー：調査担当（入口の確かめ）、検討担当（案を広げる・疑う。§4）、関わり方に応じて相談役（§3）。

### 2.3 段階③（実装）
- §7 の流れで進める。相談は CLAUDE.md の「相談の手続き」（利用者が 〈合図の語〉 と送った論点だけ）。
- 途中で大きな思いつきが出たら 〈思いつきの置き場〉 に書き、計画を大きく変えるものなら、段階② へ戻ることを提案する。

### 2.4 段階を移る
- 「移ってよい」の提案に書くこと：できたもの、確かめたこと・確かめていないこと、残り、次の段階の範囲、次の段階の関わり方の問い（おすすめ付き）。
- 移る前に HANDOFF.md（§0 の「今の段階」と引き継ぎ）を直し、作業枝にコミットし、`git fetch` してから push する。新しいセッションは、同じフォルダか作業枝で始めてもらうよう、一行添える。

## 3. 関わり方の選び方と運び方（段階①-2・段階②）

| 関わり方 | 向く場面 | 利用枠の重さ |
|---|---|---|
| (A) 主 | 新しい系統の機能や画面を一から組む。今の形から外れた発想がほしい | いちばん重い（その段階のセッション全部）。止まりやすい |
| (B) 総合 | 案が一つにまとまり、方向・抜け・別案を一度に見てほしい | 中くらい（3〜5 体に一〜二回） |
| (C) 要所 | 今の仕組みに沿った計画で、決めきれない論点が少しだけある | 軽い（論点ごとに数体） |
| なし | 小さな計画、文書の整理、前例どおり | 使わない |

- **重ね方**：(B) と (C) は重ねてよい（途中は (C)、案がまとまったときと次の段階へ移る前に (B) を一回）。(A) のときは、(B)(C) を (A) の段階の相談役で行う。
- **(A) のとき**：主担当の仕事と決まりは変わらない。区切りごと（ワークフローの結果を読んだあと、決めごとのあと、長い作業の前）に HANDOFF.md へ書いてコミット・push する。
- **(B) のとき**：3〜5 体に、観点を分けて頼む（方向・抜け・別案・危うさ・使う人の目）。時期は、案が一つにまとまったときと、次の段階へ移る前。聞かずに行い、結果を知らせる。読み方は「相談の手続き」の 3 と 4 の 1〜2。ひな形は docs/operating-kit/workflows/consult.js。
- **(C) のとき**：「相談の手続き」の 1〜4。段階①-2・② では、問いは「相談しますか」で、返事は「はい」で足りる。
- **どれでも**：相談役と検討担当の結論は決定ではない。判定は主担当、大きな決めごとは利用者。

## 4. 自由に発想する

- 発想と判定を分ける。発想の段では「今の決まりでは無理」と書かず、案を広げる。候補は 5 つ以上。一つは、今の形から外れた奇抜なものを入れる。
- 案の書き方：何を（一文）／どこに入れる（ファイルと関数）／どんな場面で効く／危ないこと／確かめ方。
- 制約は、判定の段で当てる。
- 思いつきは 〈思いつきの置き場〉 に日付つきで一行。

## 5. 判断する

- **小さな決め**：主担当が決めて、理由を計画書の「決めごと」か HANDOFF.md の §4 に一行。
- **大きな決め**（〈大きな決めごとの一覧〉）：止まって利用者に聞く。書き方は「困ったこと・案・おすすめ」。おすすめは一つ。質問は三つまで。
- **相談役を使うとき**：段階③ は CLAUDE.md の「相談の手続き」、段階①-2・② は関わり方（§3）。段階③ で相談が終わったら、結論を HANDOFF.md の §4.2 に写してから確認の一文で聞き、「はい」を待ってから次の行程に進む。
- 票や点数で決めない。利用者の答えは、日付つきで HANDOFF.md §4 に写す。

## 6. 仕事を分ける

| 役割 | 何をする | 何をしない |
|---|---|---|
| 主担当 | 計画・設計・判断・仕様・差分の確認・確かめ・利用者への説明。〈重い層〉 を書く | — |
| 実装担当 | 段階③：仕様が決まった小さな実装。段階①-2：文書の機械的な直し | 仕様に無い判断、〈重い層〉、保存の形の変更、git の操作 |
| 調査担当 | ワークフローの中で、読んで集める | 編集、判定 |
| 検討担当 | 段階①-2・② のワークフローの中で、案を広げる・疑う | 編集、判定、決定 |
| 相談役 | 段階③ は 〈合図の語〉 の論点、段階①-2・② は関わり方 (B)(C) のとき。読み取り専用の相談 | 編集、決定、自分でのワークフロー起動 |

**実装担当に渡す大きさの目安**（超えるものは、仕様を分けるか、主担当が書く）：触るファイルは 1〜3、関心は一つ。非同期の流れ、面どうしのやりとりの型、保存の形は主担当が決めて書く。〈重い層〉 は触らせない。

仕様の形は docs/operating-kit/spec.template.md。仕様は `docs/wip/<日付>/specs/<名前>.md` に置き、「---」から下を渡す。返ってきた結果は、主担当が `git diff` を全部読み、改行が変わっていないかも見てから利用者に伝える。

## 7. 段階③ の流れ

1. 段階② の計画書を読み、段を細かくする。計画が大きく違っていたら、段階② へ戻ることを提案する。段階の外の小さな仕事は、計画書なしでよい。
2. 段ごとに作業枝の中で作る。
3. 段の仕様を書き、実装担当に頼む（§6）。
4. `git diff` を全部読む。〈型検査〉。必要なら画面の確かめ。
5. 〈重い層〉 を変えたら、ビルドを確かめたかを必ず書く。確かめた範囲と確かめていないことを分けて書く。
6. 計画書の段の表を、実装の形に直す。HANDOFF.md を直す。
7. 作業枝にコミットし、`git fetch` してから push。PR は頼まれたときだけ。

## 8. 引き継ぎ（閉じるとき・主担当が替わるとき・段階を移るとき）

HANDOFF.md に書く（形は docs/operating-kit/HANDOFF.template.md）。長くしない。

1. 今の段階（段階・関わり方・作業枝・次の段階とその範囲）
2. 今どうなっているか（HEAD、未コミットの変更、動いているもの）
3. 次に何をするか（一つ。理由を一行）
4. 利用者に聞くこと（おすすめ付き）
5. 確かめたこと・確かめていないこと（分けて）
6. 返事待ちの相談（止まるときに §0 の 4 に一行。返事が来たら消す）

## 9. 書き方

- モデル名は CLAUDE.md だけに書く。ほかの文書とコミットは、段階の名前と役割名。関わり方は記号 (A)(B)(C)・なし で書く。
- 丸数字の段階には必ず「段階」を付ける。計画書の中の小分けは「段」。
- 日付は絶対日付。行番号は「見た時点の行」と書く。
- 運用の決まりを変えたら、docs/operating-kit/ のひな形も同じコミットで合わせる。
