# 主担当の進め方（主担当が読む文書）

- この文書は、段階①-2・段階②-1・段階②-2・段階③ の主担当向けです。段階①-1（下調べ）のセッションは、CLAUDE.md の「段階①-1 の決まり」だけに従います。
- 段階・役割・モデルの対応は CLAUDE.md だけにあります。この文書は、段階の名前と役割名で書きます。
- 守ることの細目は 〈決まりの文書〉。今の状態と次の一手は HANDOFF.md。食い違うときは、CLAUDE.md → この文書 → 〈決まりの文書〉 の順に従います。
- 段階①-2・②-1・②-2 の主担当は、考察・統合・問いの立て直し・自分の案を、ワークフローに任せず自分で行います。ワークフローは、広さと目隠し（広げる相が主担当の見立てに引きずられない）を得る道具です。

## 1. 最初の 5 分

1. 状態を確かめる：`git branch --show-current`、`git status`、`git fetch`。
2. 読む：CLAUDE.md → HANDOFF.md の §0・§3・§4.2 → 〈決まりの文書〉 の守ること → 関係する計画書。全部は読まない。
3. 段階を照らす：HANDOFF.md の §0 の「今の段階」と、このセッションの設定（モデル名、〈合図の語〉 の知らせ）と、今の枝。合わなければ、作業の前に利用者に伝える。段階①-2 の最初は、wip の索引の「段階①-2 への引き継ぎ」を HANDOFF.md の §0 に写す。
4. 今の状態を 3 行で言い直す。食い違いがあれば、依頼に入る前に利用者に伝える。
5. 足りないことだけを聞く（多くても 3 つ）。調べて分かることは聞かない。

新しいセッションに貼る一言は docs/operating-kit/prompts.md。

## 2. 段階ごとの進め方

### 2.1 段階①-2（整備）
- 最初に、wip の索引の引き継ぎを HANDOFF.md の §0 に写し、索引の「思いつき」を 〈思いつきの置き場〉 に写す。関わり方を照らす（記録が無ければ一つの問いで聞く）。
- 材料を読み、自由に考察・分析・発想・デザインができるよう、文書と置き場を整える。地図の切り方が、そのまま段階②-1 の発想の枠になるので、次を具体的に作る（形は docs/operating-kit/map-index.template.md。置き場は `docs/wip/<①-1 を始めた日>/map/`）：
  - 地図：一つにせず、切り口を替えて複数（使う人の場面・コードの層・データの流れ・既知の欠陥など。前からある構造の地図は「今の状態」を直して指す）。段階①-1 の外の事例・使う人の場面・類推は、確からしさの印を付けたまま使う。
  - 対象の部分の候補（段階②-1 の parts になる）。
  - 観点の一覧 `map/lenses.json`：consult.js と ideate.js の lenses にそのまま渡せる `{ key, ask }` の形。ask に答えの例を書かない。
  - 問いの一覧：段階①-1 の引っかかりと、地図を作っていて浮かんだ問い（答えは書かない。仮の答えは `map/notes.md` に。利用者に聞くものは HANDOFF.md の §4.1 に写す）。
  - 考察の記録 `map/notes.md`：地図を作っていて見えた分析（緊張関係・原因や前提の仮説・食い違い・問いの言い換え）と、問いへの仮の答え。推し量りの印（確かめた・読んだだけ・推し量り）を付け、判定（採否・順位・おすすめ）は書かない。段階②-1 の広げる相には読ませない（地図の表に載せず、ideate.js の read に入れない。入れると止まる）。
  - 制約の一覧 `map/constraints.md`：〈決まりの文書〉 の守ること・〈大きな決めごとの一覧〉・〈重い層〉・既存の数・外への送信などを一か所に集める。段階②-1 の広げる相には見せず（一周目は観点ごとの read にも入れない）、段階②-2 の判定で当てる（§4.1 の「制約は判定で当てる」を仕組みにしたもの）。段階①-2 の時点の写しなので、段階②-2 では今の文書と照らし直す。
- 思いつきの重なりはまとめる（判定はしない。まとめは 〈思いつきの置き場〉 の中に、元の行を指す一行で書き（元の行は残す）、地図と一覧には書かない。地図と一覧は段階②-1 の広げる相が読むため）。材料を置く場所も整える。地図と一覧のパス（`map/README.md` と地図のファイル）は、HANDOFF.md の §0 の「次の段階」に書く（段階②-1 が案の一覧の頭に写す）。
- 計画、段の分け方、案の採否は決めない。途中の思いつきは 〈思いつきの置き場〉 に一行。
- ワークフロー：調査担当で読み足し、検討担当に整え方の案を広げさせ、疑わせる（docs/operating-kit/workflows/consult.js。広げさせる観点は blind にする）。判定は主担当。関わり方 (A) では、文書の機械的な直しを実装担当に回し、主担当の時間を地図と考察に使う。

### 2.2 段階②-1（考察と発想）
- 最初に、関わり方を照らす（記録が無ければ一つの問いで聞く）。案の一覧を docs/operating-kit/ideas-index.template.md から `docs/wip/<②-1 を始めた日>/ideas/README.md` に作り、§0 の「次の段階」にある、段階①-2 の地図と一覧のパス（`map/README.md` と地図のファイル。constraints.md は除く）を、案の一覧の頭の「読むもの」に写す（続けるセッションと、段階②-2 から戻ったときは、そこから引く）。考察ノート `ideas/notes.md`（形は ideas-index.template.md の「考察ノートの形」）も、同じフォルダに作る。HANDOFF.md の §0 の「案の一覧」の行にパスを書き（考察ノートは同じフォルダの notes.md）、ワークフローを起こす前にコミットする（push は、返事待ちで止まるときと、移るとき）。続けるセッションは、同じフォルダに足す。同じ日に別の対象で段階②-1 を始めるなら `ideas-<短い名前>/` にする。
- 主に読むのは、段階①-2 で整えた地図と一覧（`map/README.md`・地図・lenses.json・問いの一覧）と 〈思いつきの置き場〉・〈見送りの台帳〉（台帳がまだ無ければ飛ばす）。観点は lenses.json から選んで足し、部分は地図の部分の候補から選ぶ。置き場の「前提の誤り」の行（段階③ の段の終わりに書かれたもの）は、案ではなく材料なので案の一覧に載せない（id を振らず、known にも入れない）。対象に関わるものは、手順の 1 で部分と観点を立てる材料にし、案の一覧の「改善の根・横断的な気づき」に、元の行を指して一行で書く。段階①-2 の制約の一覧 `map/constraints.md` は、段階②-1 の共通の read に入れない（どの周でも）。二周目からは、制約を外す方向の観点の read（観点ごとの read）にだけ入れてよい。ideate.js は、一周目の read と、どの周でも共通の read にあれば止める。広げる相に読ませないものは、止める一覧で決める（案の一覧のフォルダは `sources/` の下だけ許す）：HANDOFF.md・考察ノート・cards.md・先出しの案 main-R\*.json・raw-R\*.json・tries/・map のフォルダごと・思いつきの置き場・見送りの台帳は read に入れない（ideate.js が止める。置き場と台帳は、既定の名前 ideas-inbox.md・ideas-shelf.md だけ止まる。別の名前なら、主担当が入れない）。足りなければ、段階①-1 の材料とコードも読む。置き場と台帳の案は、広げる相に渡さない（引きずられないため）。対象に関わる案（台帳なら、もう一度見る条件に当たる案。置き場の行で「→ <日付> 判定」の付いたものは置き場からは載せず、台帳の行で見る）を、主担当が出どころを付けて案の一覧に載せ（id は §4.1）、ideate.js の known に「<id> <短い名前>」の形で入れて重なりを見る（主担当が自分で考えた先出しの案は、known でなく `mainIdeas` に渡す。同じ id を両方に入れると ideate.js が止める）。置き場と台帳は書き換えない（書き戻すのは段階②-2）。
- 案を観点ごとに広げる（§4.1）。足りない材料は、調査担当で読み足し（リポジトリの外の資料は、利用者が許したときだけ。survey.js の `external` と `externalScope`）、案の一覧のフォルダの `sources/<話題>.md` に置く（段階①-1 の索引は直さない。sources/ は次の周の read に入れてよいので、調査担当が集めた事実と出どころだけを書き、主担当の見立て・案・読み足した理由は書かない。読み足す survey.js の話題の ask には「案の一覧・思いつきの置き場・見送りの台帳・HANDOFF.md は読まない」と書く）。ワークフローが使えなければ、主担当が観点ごとに自分で広げ、同じ形で書く（自分で広げるときも、見立ての要約は広げ終えてから書く。目隠しの代わり）。照らす・伸ばす・疑うも主担当がし、カードの同じ欄に「主担当」と書く（別の担当が疑っていないことを、終わりの目安の照らしと「移ってよい」の提案に書く）。
- 主担当が自分で考える（先出し。手順は §4.1）：規模を見立て、困りごとを確かめ、問いの言い換え・部分・観点の案・考察を考察ノートに書き、自分の案を `ideas/main-R<周>.json`（mainIdeas の形。最小は id・title・what・kind）に書いてコミットしてから、ワークフローを起こす。見立ての要約（案の一覧の「主担当の見立て」の節）だけを、広げ終えてから書く。考察ノートは、いつ書いてもよい。
- 行程の判断（どの観点で広げるか、二周目を回すか、終わりの目安を満たしたか）は主担当がする。しないのは、案の採否と箱分け（判定は段階②-2）、順位付け、計画、段の分け方。制約は段階②-2 の判定で当てる。束ねる・比べる・困りごとと案の対応を書く・トレードオフの軸を描くのは判定ではないので、してよい（考察ノートか、案の一覧の「改善の根・横断的な気づき」に）。
- ワークフローの結果（全文は、通知が示す出力のファイルの JSON の result。通知の本文は途中で切れる。journal.jsonl は、空や失敗の理由を見るときに読む）を読んだら、要約する前に、全部の案を残す：`result` だけを `raw-R<周>.json` に写し（`node docs/operating-kit/tools/ideas-table.mjs extract <出力のファイル> <案の一覧のフォルダ>/raw-R1.json`。jq があれば `jq '.result' <出力のファイル> > …` でもよい。手で打ち直さない。ファイルを丸ごと写さない：ほかの欄にモデル名が入る。同じ周の二回目からは `raw-R<周>-2.json`・`-3.json` と番号を上げ、上書きしない）、案の一覧の「観点 × 案の表」に一案一行で書き（行は `ideas-table.mjs table` で作ってよい。主担当が手で足すのは、種類の付け直し・出どころ・束だけ）、コミットする（セッションが替わると読めなくなる。push は、返事待ちで止まるときと、移るとき）。
- 終わりの目安（§4.2）を照らし、結果を案の一覧に書いてから、「移ってよい」と提案する。HANDOFF.md の §0 の「次の段階」は段階②-2 に直す（案の一覧のパスは §0 の「案の一覧」の行だけに書く。段階②-2 はそこから読む）。
- ワークフロー：検討担当と調査担当（docs/operating-kit/workflows/ideate.js。広げる・照らす・伸ばして疑う。主担当の案は `mainIdeas` で通す。§4）、調査担当（読み足す）、検討担当（consult.js の `form: 'analysis'`。考察の観点。§4.1 の 2）、相談役（(A) の始めの問いの立て直し、関わり方 (B) の所。§3）。

### 2.3 段階②-2（計画とデザイン）
- 最初に、HANDOFF.md の §0 にある案の一覧を読む。HANDOFF.md の §4.1 と、案の一覧の「段階②-2 が読むときの注」の問いのうち、判定に効くものは、判定の前に利用者に聞く（三つまで）。そのうえで制約（段階①-2 の制約の一覧 `map/constraints.md` と、今の 〈決まりの文書〉 の守ること・〈大きな決めごとの一覧〉・〈重い層〉。constraints.md は段階①-2 の時点の写しなので、食い違えば今の文書に従う）を当てて、案を箱に分ける（§5）。判定は、案の一覧の判定の表（id・箱・理由一行・計画に入れたか。表の頭に、判定の基にした段階②-1 のコミット。書き始める前に `git log -1 --format=%h -- <案の一覧のフォルダ>` で調べる）だけに書き、コミットする。案そのものは書き換えない。考察ノートは、「考察」と「捨てた筋」を判定の前に読み、「予感」は判定の表を書いてから読む（予感が判定を先回りしないため）。
- 箱に分けたら、「すぐ」「次」の案だけを、検討担当に疑わせる（consult.js。主担当の見立ては見せる）。関わり方 (A) では必ず行う。訂正があれば判定の表に書く。ワークフローが使えなければ主担当が疑い、判定の表の理由に「主担当が疑った」と書く（別の担当が疑っていないことを「移ってよい」の提案にも書く）。
- 計画に入れる案は、主担当が「すぐ」と「次」から選び、理由を計画書の「考察から変えたところ」に書く（基にした案の一覧のパスと id も）。計画に入れる案が決まったら、疑いの要点を、入れた案は計画書の「考察から変えたところ」に、ほかは判定の表の理由に一行で書く。大きな決めごとに当たるものは、止まって聞く。
- 計画書を 〈計画書の形〉 で書く。段はおおまかでよい（段階③ の始めに細かくする）。
- 画面が変わるなら、見本を 〈見本の置き場〉 に作る（〈コードの場所〉 は変えない）。
- 大きな決めごと（〈大きな決めごとの一覧〉）は、困ったこと・案・おすすめで聞き、答えを HANDOFF.md の §4 に写す。
- 計画を組む途中で、広げ直しが要るほどの抜けが分かったら、段階②-1 へ戻ることを提案する。小さな抜けなら、その場で案を足し、出どころを「段階②-2 で足した」と書く。
- 計画に入れる案が決まったら、計画に入れなかった案をすべて（「後」「見送り」と、計画に入れなかった「すぐ」「次」）〈見送りの台帳〉 に一行ずつ写す（日付・短い名前と一文・箱・理由・もう一度見る条件・元のパスと id と、判定の表の頭の基にしたコミット。台帳が無ければ、このとき頭に書き方を三行書いて作る）。台帳から来た案は、その行を書き換える（新しい行を足さない。計画に入れたら「→ 計画 <名前>」）。置き場から来た案は、置き場の元の行（まとめた案なら、まとめた元の行すべて）の末尾に「→ <日付> 判定：<箱>（<案の一覧のパス> <id>）」と足す。改善の根に写された置き場の「前提の誤り」の行には、「→ <日付> 読んだ（<案の一覧のパス>）」と足す。台帳と置き場への書き戻しは、段階②-2 の主担当だけがする。「移ってよい」の提案の前に、HANDOFF.md と同じコミットで書く。
- 「移ってよい」の提案には、箱ごとの数と、「後」「見送り」にした案（とくに 〈思いつきの置き場〉 から来た案）の一覧を添える。利用者が箱を変えたら、判定の表（理由に「利用者の答え（HANDOFF.md §4 の日付）」）・台帳の行・HANDOFF.md の §4 を同じコミットで直す。
- 段階②-1 へ戻るときは、判定の表を消さずに残す（見出しを「<日付> の判定。基にしたコミット <ハッシュ>」に）。段階②-1 は同じフォルダに周を上げて足し、終わりの目安の照らしは日付つきで書き足す。段階②-2 に戻ったら、新しい周の案だけの判定の表を足す。前の判定を変えるときは、前の表は直さず、新しい表にその id の行を足し、理由に「<日付> の判定から変える：<理由>」と書く（台帳の行は、あれば直し、無ければ上のとおり足す。置き場から来た案なら、置き場の行にも新しい箱の「→ <日付> 判定」を足す。同じコミットで）。
- ワークフロー：調査担当（入口の確かめ）、検討担当（計画の案を疑う。consult.js）、関わり方に応じて相談役（§3）。

### 2.4 段階③（実装）
- §7 の流れで進める。相談は CLAUDE.md の「相談の手続き」（利用者が 〈合図の語〉 と送った論点だけ）。
- 途中で大きな思いつきが出たら 〈思いつきの置き場〉 に書き（段の終わりには「前提の誤り」も。§7 の 6）、計画を大きく変えるものなら、段階②-2 へ（広げ直しが要るなら段階②-1 へ）戻ることを提案する。

### 2.5 段階を移る
- 「移ってよい」の提案に書くこと：できたもの、確かめたこと・確かめていないこと、残り、次の段階の範囲、次の段階の関わり方の問い（おすすめ付き）。
- 移る前に HANDOFF.md（§0 の「今の段階」と引き継ぎ）を直し、作業枝にコミットし、`git fetch` してから push する。新しいセッションは、同じフォルダか作業枝で始めてもらうよう、一行添える。
- 段階②-1 から ②-2 へは、セッションの設定が同じなので、新しいセッションにするだけでよい（関わり方 (A) を変えるときを除き、モデルの切り替えは要らない）、と提案に一行添える。

### 2.6 段階②-1 と ②-2 を一つのセッションでまとめるとき
- 決めるのは利用者。段階①-2 の「移ってよい」の提案で、おすすめ付きで聞く（まとめてよい目安：観点が三つで足りる、大きな決めごとに当たる見込みが無い、触る所が一つの面）。
- HANDOFF.md の §0 の段階は「段階②（②-1・②-2 をまとめる）」と書く。セッションは段階②-2 の行の設定にする。
- 関わり方は、利用者が選んで HANDOFF.md の §0 に書いたものに従う（記録が無ければ一つの問いで聞く）。選んでいないときの既定は (A)（セッションは 〈上〉。小さな計画で利用枠を抑えたいときは、利用者が なし か (C) を選ぶ）。(A) のとき、広げる周の始めの問いの立て直しは任意（行うなら 〈主〉 の相談役に blind で一回）、判定の周では「すぐ」「次」の案を検討担当に疑わせる。(B) を選んだときは、広げる周は始めの問いの立て直しだけ、(C) は判定の周から使い、終える前に (B) を一回（二つの段階で一回にまとめる）。広げる周は一周なので、掘る方向の問いは聞かない。
- 広げる周（§2.2・§4。観点三つ・一周）を終えたら、案の一覧をコミットしてから判定の周（§2.3）に入る（芯の 9）。終わりの目安は §4.2 の 1 と 2 だけを照らす。1 か 2 を満たさなければ、判定の周に入る前に止まり、空いた部分か、足りない種類が出やすい部分に向けた観点でもう一周足すか、そのまま判定の周へ進むかを、おすすめ付きの一つの問いで聞く。判定の周のあと、§2.3 のとおり 〈見送りの台帳〉 に書く。
- 一言は docs/operating-kit/prompts.md §1.9。

## 3. 関わり方の選び方と運び方（段階①-2・段階②-1・段階②-2）

| 関わり方 | 向く場面 | 利用枠の重さ |
|---|---|---|
| (A) 主（標準） | 考える段階（整備・考察と発想・計画とデザイン）の主担当に、いちばん深く考えるモデルを使いたいとき。考察・分析・発想を主担当が自分で行う。〈上〉 が使えない、または利用枠を抑えたい小さな計画では、(B)(C)・なし | 重い（その段階のセッション全部）。止まりやすいので、区切りごとに HANDOFF.md へ書く |
| (B) 総合 | 案が一つにまとまり、方向・抜け・別案を一度に見てほしい。段階②-1 では、始めに問いの立て直しを、一周目のあとに抜けと広げ足りない所を見てほしい | 中くらい（3〜5 体に一〜二回） |
| (C) 要所 | 今の仕組みに沿った計画で、決めきれない論点が少しだけある | 軽い（論点ごとに数体） |
| なし | 小さな計画、文書の整理、前例どおり | 使わない |

- **重ね方**：(B) と (C) は重ねてよい（途中は (C)、案がまとまったときと次の段階へ移る前に (B) を一回）。段階②-1 では (C) を使わないので、(B) だけ。(A) のときは、(B)(C) を (A) の段階の相談役（〈主〉）で行う（段階②-1 の始めの問いの立て直しは既定で行い、一周目のあとの (B) は任意）。
- **(A) のとき**：主担当の仕事と決まりは変わらない。考察と先出しの案を主担当が自分で書くのは、どの関わり方でも同じ（§4.1）。(A) で違うのは、(1) セッションが 〈上〉 になる、(2) 別の担当の目（検討担当 〈主〉）を、段階ごとに一回は入れる、(3) 区切りごと（ワークフローの結果を読んだあと、決めごとのあと、長い作業の前）に HANDOFF.md へ書いてコミットする（利用枠で止まるのは前もって分からないので、区切りごとのコミットが命綱。クラウドの容器など、消える環境では区切りごとに push も。push は、ふつう返事待ちで止まるときと、移るとき）、の三つ。(A) の相談役は上位のモデルではないので、「上位の意見」ではなく「別のモデルの独立した意見」として使い、受け止めと判定は主担当がする。
- **段階②-1 の (A)**：始め（一周目の前）に、主担当が先に問いの言い換え（三つ以上）・parts・観点の案を考察ノートに書く。そのあと、相談役（〈主〉）に一回頼む（聞かずに行い、結果を知らせる）：consult.js の `form: 'analysis'`、観点は「問いを言い換える」（`blind: true`。主担当の言い換えを見せず、独立に言い換えさせる）、「部分の切り方」「観点の立て方」（主担当の案を見せて疑わせる）。受け止めて topic・parts・観点を直し、直したことを案の一覧の頭の「集め方」に書く。一周目のあとの (B) は任意（抜けと広げ足りない所は、まず主担当が自分で照らす。足りなければ頼む）。考察そのものを疑わせたいときは、別の呼び出しで、考察ノートを read に入れ、blind にしない観点「考察を疑う」（ask：考察ノートの仮説・緊張関係・問いの捉え方の偏りと見落としを挙げる）を一つ頼んでよい（blind の観点と同じ呼び出しには、考察ノートを read に入れられない）。
- **(B) のとき**：3〜5 体に、観点を分けて頼む（方向・抜け・別案・危うさ・使う人の目）。時期は、案が一つにまとまったときと、次の段階へ移る前。聞かずに行い、結果を知らせる。読み方は「相談の手続き」の 3 と 4 の 1〜2。ひな形は docs/operating-kit/workflows/consult.js。
- **段階②-1 の (B)**：時期は二つ。聞かずに行い、結果を知らせる。
  1. 始め（一周目の前）：問いの立て直し。主担当が立てた対象（topic）・部分（parts）・観点の案を、相談役に丸ごと見てもらう（観点は、問いを言い換える・部分の切り方・観点の立て方）。受け止めて topic・parts・観点を直し、直したことを案の一覧の頭の「集め方」に書く。
  2. 一周目の案を書いたあと：案の一覧を丸ごと見てもらう（観点は、抜けている観点・広げ足りない所・伸ばしがいのある束）。二周目の観点と、「掘る方向」の問い（§4.1 の手順の 4）に使う。
  - 小さな計画（観点三つ・一周）では 1 だけ。
  - 相談役が出した新しい案は、出どころを (B) としてカードに足す（判定しない）。HANDOFF.md の §4.2 の「主担当の判定」の欄には、受け止め（例：直した観点、二周目に足す観点）を書く。渡し方は docs/operating-kit/prompts.md §4。
- **(C) のとき**：「相談の手続き」の 1〜4。段階①-2・②-2 では、問いは「相談しますか」で、返事は「はい」で足りる。
- **どれでも**：相談役と検討担当の結論は決定ではない。判定は主担当、大きな決めごとは利用者。

## 4. 自由に考察・発想する（段階②-1）

### 4.1 広げ方

**手順**（段階②-1。小さな計画（観点三つ・一周）は 1〜3・4 の照らし・6 だけ。小さな計画で関わり方 (B) なら、2 の問いの立て直しだけを行い、4 の (B)・掘る方向の問い・5 は行わない。§2.6 と同じ。1 の先出しは、どの関わり方でも行う。2 の別の目は、関わり方 (A)(B) で行う）
1. **規模と材料、先出し**：規模（ふつう／小さな計画）を見立てる（迷えば利用者に一つ聞いてよい）。困りごとを確かめる（利用者への問いは三つまで。例：探すとき何を覚えているか、最近困った一件。答えは topic の「困っている場面」にだけ入れ、parts と観点は自分の考察で立てる）。段階①-2 の地図と一覧から、対象の部分（parts）と観点を選ぶ（一周目は、部分を観点にしたものと発想の型を半分ずつほど。照らす五つの種類を思い浮かべて選ぶ）。選ぶ前後に、問いの言い換え（三つ以上）・部分・観点の案・考察を考察ノートに書く。自分の案（十ほどまで）を `ideas/main-R<周>.json`（`mainIdeas` の形：id は `R<周>-主-<番号>`。最小は id・title・what・kind）に書く（見立ての要約・おすすめ・順位はまだ書かない）。ここまでをコミットしてから、ワークフローを起こす（cards.md には書かない。ワークフローを通すと raw に入り、表になる）。
2. **別の目（問いの立て直し）**：関わり方 (A) か (B) なら、相談役に問いの立て直しを一回頼み、topic・parts・観点を直す（§3）。考察の観点（緊張関係／原因や前提の仮説／食い違い。結果は考察ノートへ。広げる相には見せない）を、consult.js の `form: 'analysis'`、`blind: true` で、一周目の前に頼んでもよい。
3. **一周目を回す**（ideate.js）。先出しの案は `mainIdeas` に渡す（`main-R<周>.json` の中身をそのまま。2 で parts を変えたら、先に `main-R<周>.json` の parts を直す。広げる相には見せず、照らす・伸ばして疑う相が通す。広げた案と重ならなかった数が `counts.main.unique`）。生の案を写し、観点 × 案の表に書いて、コミットする（§2.2）。
4. 終わりの目安（§4.2）を照らす。(B) なら、抜けと広げ足りない所を一回見てもらう。そのうえで、案を三〜五の束（部分・改善の根・観点でまとめたもの）にして、利用者に「どの束をもっと掘りますか」と一つ聞く（下の「掘る方向を選ぶ問い」）。
5. **二周目を回す**。観点を、掘る方向・空いた部分・足りない種類が出やすい部分に向けて替える。
6. 終わりの目安を照らして案の一覧に書き、「移ってよい」と提案する。

**掘る方向を選ぶ問い**（採るかどうかではない軽い問い。大きな決めごとの問いとは分ける）
- 聞き方：束ごとに一行（関わる案の id と、何が見えた束か）、おすすめ一つと理由一行、「採るかどうかではありません（判定は段階②-2）。いくつ選んでもよく、『任せる』なら空いた部分と足りない種類に向けます」と添える。案の一覧の「案の束と掘る方向」の節に束を書いてから聞く。
- 答えは HANDOFF.md の §4 に「掘る方向（判定ではない）」として日付つきで写し、案の一覧の同じ節にも写す。止まるときは §0 の 4 に「返事待ち（掘る方向）」と一行書いてコミット・push しておく。
- 掘るのは観点で：選ばれた束の部分・問い・改善の根を、二周目の観点（{ key, ask }）や parts に寄せる。束の案そのものは広げる相に見せない（目隠しのまま。重なりは known で照らす相が見る）。束の案を土台に深めたいときは、深める周（下の `deepen`）を別に足す。
- 選ばれなかった束も消さない（判定ではないので、段階②-2 は全部の案を判定する）。
- 利用者が前もって HANDOFF.md の §0 に「掘る方向は任せる」と書いていれば、聞かずに、空いた部分と足りない種類（または `deepen`）に向ける。

- 発想と判定を分ける。広げるのは段階②-1、判定は段階②-2。二つの段階をまとめるときも、広げる周と判定の周を分け、判定の前に案の一覧をコミットする。考察（問いの捉え直し・緊張関係・原因や前提の仮説・食い違い・トレードオフの軸・困りごとと案の対応）は判定ではない。判定は、箱・採否・順位・おすすめだけ。
- 広げるときは「今の決まりでは無理」と書かず、案を広げる。制約は、段階②-2 の判定で当てる。
- 広げる → 照らす → 伸ばして疑う、の三つの相で進める。ワークフローは docs/operating-kit/workflows/ideate.js（渡し方は docs/operating-kit/prompts.md §4）。広げる担当には、良し悪しで案を捨てさせず、入れる場所も考えさせない（入れる場所は照らす相の調査担当が探す。危ないことと確かめ方は伸ばす・疑う相が書く）。考えること自体は自由にさせる。
- 観点は二つの軸で立てる。対象の部分（段階①-2 の地図と一覧の「部分の候補」。地図に無い切り口は、主担当が材料から立てる。ideate.js の parts）と、発想の型（一周目の既定は 使う人の場面・逆にする・ほかから借りる・制約を一つ外す・極端にする・ほかの立場。ほかに 組み合わせる・時間をずらす・既知の欠陥から・問いを変える・作らずに済ませる を名前で選べる）。一周目は、部分を観点にしたもの（{ key, ask }）と発想の型を半分ずつほど混ぜる。同じモデルが言い換えた問いに答えるだけでは案が似るので、観点ごとに別のモデル（`lensModels`）や別の地図（観点の `readOnly` と `read`）を割り当てると、案が分かれやすい。
- 一つの観点に 4〜6 案を目安に、実りが多ければ 12 まで（12 に届いてなお出せるなら `more`。二周目でその観点を掘る。only で頼み直さない：同じ id に別の案が入る）。合わない観点は少ないまま返させる（水増ししない）。案に筋道（`why`。推し量り）を付けさせ、観点の外の考えは `aside` に自由文で返させる。
- 観点の数は仕事の大きさで選ぶ。ふつうの計画は、一周に六つ（12〜18 体。照らす相・伸ばす疑う相の 1 体が 8 案ほどに収まる）で、二周以上を目安にする（合わせて 12 観点ほど。回さないなら理由を一行）。小さな計画は三つで一周（5〜9 体）。一度に起こせるのは 6 観点まで（伸ばす・疑う相を外せば 8）。つなぐ一体（`synth`）を足すと、塊が 5 つまで。
- 目隠し：主担当の見立ても前の周の案も、広げる相に見せない。topic には対象と困っている場面だけを書き、見立ては background に（伸ばす・疑う相だけが見る。raw の asked に残る短い見立て。案の一覧の「主担当の見立て」の節は、広げ終えたあとの要約で、別のもの）。観点の ask に答えの例を書かない（問いの言い換えは、問いの形で ask に溶かしてよい。答えの例ではないので目隠しを破らない）。広げる相に読ませないものは、止める一覧で決める（案の一覧のフォルダは `sources/` の下だけ許す）：HANDOFF.md、考察ノート、cards.md、main-R*.json、raw-R*.json、tries/、map のフォルダごと、思いつきの置き場、見送りの台帳は read に入れない（ideate.js が止める。置き場と台帳は既定の名前だけ止まる）。段階①-1 の索引の「思いつき」の節は、指示文で読ませない。HANDOFF.md を読む決まりも、この相では行わない。制約の一覧は上の §2.2 のとおり。地図と一覧はパスを名指しして read に入れる（担当は HANDOFF.md の §0 からたどれない）。
- 主担当の案（先出し）は、広げる相には見せない。`mainIdeas` で渡すと、照らす相と伸ばして疑う相が通す（別の担当の疑いを受ける）。広げ終えてから足す案は、`R<周>-主-<番号>` で cards.md に書く（形は同じ。判定はしない。先出しの案と番号を分ける）。
- 案の id：ワークフローの案は `R<周>-L<観点の番号>-<番号>`、主担当が足す案（置き場・台帳から載せた案も。出どころに元の行）は `R<周>-主-<番号>`、関わり方 (B) の相談役が出した案は `R<周>-B-<番号>`、つなぐ一体（`synth`）が組んだ案は `R<周>-X-<番号>`（照らしも疑いも経ていない。`ideas-table.mjs` が表と known に出す。段階②-2 の判定の対象。§4.2 の 2 の種類の数えには入れない。根と空白の要点は案の一覧の「つなぐ一体の根・空白と、観点の外の考え」の節へ）、段階②-2 で足す案は `足-<番号>`。ワークフローが使えないときも、主担当が同じ形で振る。
- 照らす案の種類（五つ）：奇抜（今ある面・保存の形・流れのどれかを変えないと入らない案）、やめる・減らす、今ある仕組みを組み合わせる、制約を外す（例：〈重い層〉 を変えてよいなら）、作らない（作らずに、使う人が自分でやる・今ある道具や手順で済ませる）。出し忘れやすい方向の点検表であって、割り当てではない。一周目のあと §4.2 の 2 で照らす。足りない種類があれば、二周目に、その種類が出やすい部分や場面の観点を足す（ask でその種類を名指しした観点でもよい。名指し由来と照らしに書く）。
- 案の形：何を（一〜二文）／筋道（任意。推し量り）／どんな場面で効く／関わる所／種類（「奇抜」「やめる・減らす」「組み合わせる」「制約を外す」「作らない」「そのほか」の六つ。ideate.js の kind と同じ）／効く部分。照らす相が、入れる場所・今あるもの・前提・重なりを足す。伸ばす・疑う相が、成り立つ条件・大胆にした形・組むと強くなる案・崩れうる前提・いちばん安い確かめ方を足す。
- 一周目のあと §4.2 を照らし、空いた部分・少ない種類に向けて観点を替えて二周目を回す。二周目は round を 2 にし、known に前の周までの案と主担当が載せた案を「<id> <短い名前>」の形で渡す（同じ周の `mainIdeas` の id は known に入れない。前の周の先出しの案は、raw に入っているので known に入る）。照らす相だけが見て、同じ形で重なりを返す。広げる相には見せない。`ideas-table.mjs known raw-R1.json …` で作れる（置き場・台帳から載せた案とつなぐ一体の案も入る。広げ終えてから cards.md に足した案と (B) の案は、手で足す）。knownToExpand は、コードや対象が大きく変わったあとに、前の案と重ならない案だけを出し直すときだけ true にする（同じ案の一覧で周を足すふつうの二周目には、セッションが替わっても、段階②-2 から戻っても使わない。true のときは known から置き場・台帳の案を外し、飽和で照らさない）。
- 二周目からの選べる形（どれも飽和の照らしには使わない周になる）：深める周（`deepen`：掘る方向に選ばれた束の案を、広げる相に見せる。fresh は null）、逐次に積む（`chain`：観点を順に回し、先の観点の案を後の観点に見せる。目隠しが弱まるので、その周の観点は 3 つほどに絞り、一周目では使わない）。つなぐ一体（`synth`）は、全部の案を見て、塊をまたぐ根・組み合わせ・観点の空白を返す（束と順位は書かない。主担当の束づくりを先回りしないよう、束は主担当が作る）。

### 4.2 終わりの目安（「移ってよい」と言えるとき）
照らして案の一覧に書く。満たさないまま移るなら、満たさない点と理由を「移ってよい」の提案に書き、利用者が決める（これが既定の道。数合わせのための水増しや周の追加はしない）。
1. 網羅：対象の部分（parts）のどれにも、案が一つ以上ある。無い部分は、二周目でその部分を観点にして回すか、広げない理由を一行書く（parts を渡さなかったときは、観点のどれにも案があること）。案の乏しかった観点（thin）は、網羅とは別に書く。
2. 種類：主担当がカードを読んで付けた種類で、照らす五つ（「奇抜」「やめる・減らす」「組み合わせる」「制約を外す」「作らない」）がそれぞれ一つ以上ある。観点の ask がその種類を名指しで求める案（観点「組み合わせる」の組み合わせる案、観点「逆にする」のやめる・減らす案、観点「制約を一つ外す」の制約を外す案、観点「作らずに済ませる」の作らない案）は、「名指し由来」と書いて数える。名指しでない観点からも一つ以上あることが望ましい（無ければ、その旨を照らしに書く）。どの観点にも頼む「奇抜を一つ」は、名指しに当たらない。奇抜は、今ある面・保存の形・流れのどれかを変えないと入らない案（照らす相が「新しく作る所」と書いた案が目安）。
3. 量か飽和：重なりを除いた案（照らす相の重なりを見て、主担当が数え直したもの）が、規模に合った数ある（ふつうの計画は 30 前後、小さな対象は 20 前後）。または、最後の周の新しい案（調査担当が前の周との重なりを見つけず、主担当も重ならないと見た案）が 3 つ以下だった。
4. 考察（数えない）：考察ノートに、問いの捉え直し・緊張関係・原因や前提の仮説のどれかを書いた。書かないなら理由を一行。
- 1 と 2 は満たすのが望ましく、3 はどちらか一つ。ふつうの計画では二周以上を目安にする（1〜3 を満たしていても二周目に何を足すかは、主担当が決める。回さないなら理由を一行）。小さな計画（観点三つ）は一周でよく、3 を問わない。段階②-1 と ②-2 をまとめたとき（§2.6）も、観点三つ・一周で、3 を問わない。
- 照らすのは主担当。ワークフローが返す数（counts）は材料で、票ではない。raw は重なりを除く前の数（先出しの案を含む。rawSpread は広げた案だけ）、byKindSelf は広げた担当の自己申告、fresh は調査担当が重なりを見つけなかった案の数（広げた案だけで数える。照らされなかった案があるとき・広げる相が空だった観点があるとき・knownToExpand・`deepen`・`chain` のときは null）。`counts.main` は先出しの案の数（total）と、広げた案のどれとも重ならなかった数（unique。主担当が独自に出した案の量の目安。広げる相が空だった観点があるときなどは null。そのときは、観点 × 案の表で主担当が数える）。種類を付け直したら案の一覧に書く。
- 広げる相が空だった観点のある周は、網羅と飽和の照らしに使わず、その観点だけを頼み直す（ideate.js の only。返す値は次の番号の `raw-R<周>-<回>.json` に）。網羅と飽和は、同じ周の回を合わせて主担当が照らす（回どうしの重なりは、主担当が観点 × 案の表で見る）。
- 照らす・伸ばす・疑う相が空だった塊（empty.light・empty.grow）や、答えの抜けた案（missing・counts.unlit）は、頼み直さない（同じ args や only で起こし直すと、同じ id に別の案が入る。mainIdeas は only と一緒に渡せない）。その案の照らしと疑いは主担当が足し、cards.md に同じ id の見出しで、補った欄だけを「主担当」として書く（raw-R*.json は直さない）。照らす相が空・抜けだった周は fresh が null で返るので、飽和は主担当が照らす（伸ばす・疑う相だけが空なら、fresh はそのまま使える）。
- 照らした結果（数と、主担当の照らし。どれを満たし、どれを満たさないか）は、案の一覧に書く。
### 4.3 思いつき
- 段階②-1 の対象の外の思いつきは 〈思いつきの置き場〉 に日付つきで一行。

### 4.4 捨てる前提の試し（段階②-1・②-2）
- 読む・照らすだけでは確かめられない前提を試す。技術の前提（動くか、速さ、ライブラリや API がその使い方を許すか）と、手触り（素描や合成データで、探しやすさ・分かりやすさを触って比べる。scratchpad でよい）。案を作り込むためには使わない。
- 作業枝で 〈コードの場所〉 を変えない決まりは、そのまま残す。試しは主担当が、別の worktree で、〈試しの枝〉 の上だけで行う（作業枝の HEAD から `git worktree add -b <〈試しの枝〉の形の名前> <置き場>` で作る。作ったら `git -C <置き場> log -1` で元の版を確かめる。サブエージェントには頼まない：Agent ツールの worktree は、作業枝の HEAD でない版から作られることがある）。リポジトリのコードに触らない試し（数行の実験で、速さや動くかを見るだけのもの）は、worktree でなく scratchpad で行ってよい（結果の書き方は同じ）。
- 時間を区切る（一つの試しは 30 分ほど）。超えそうなら止めて、分かったことだけを書く。
- 結果は事実として書く：段階②-1 は案の一覧のフォルダの `tries/try-<短い名前>.md`、段階②-2 は `docs/wip/<②-2 の日付>/tries/try-<短い名前>.md`（計画書の「決めごと」から指す。案の一覧のフォルダには足さない）。何を試したか・どの案の id か・分かった事実（動いた・動かない・数）・確かめていないこと。コードは写さない（要るなら短い抜き書きだけ）。tries/ は案の id を含むので、広げる相の read に入れない（sources/ とは分ける）。試しは判定ではない（段階②-1 では、cards.md に同じ id の見出しで「試し：tries/try-<短い名前>.md」と一行足すだけ）。
- 〈試しの枝〉 は、作業枝にも 〈入れない枝〉 にも取り込まず、push しない。終わったら worktree と枝を消す（残したいときは利用者に聞く）。試しがそのまま本物にならないように、本物は段階③ で仕様から作る。
- 〈重い層〉 に触る試し、外への送信や鍵が要る試し、既存のデータに触る試しはしない（大きな決めごとに当たるので、要るなら利用者に聞く）。

## 5. 判断する

- **案の判定**（段階②-2。判定は、箱・採否・順位・おすすめだけ。考察は判定ではない）：段階②-1 の案に制約を当て、箱に分ける。すぐ（小さく、今ある仕組みで作れて、効果が大きい）／次（段を分ければ入る）／後（大きい、または今は要らない）／見送り（危ない、効果が薄い、今の決まりに反する）。理由は一行ずつ。票や点数で分けない。照らす相の「新しく作る所」や、伸ばす・疑う相の崩れうる前提の多さは、それだけでは見送りの理由にしない（外れた案ほどそうなる）。見送りにする案には、もう一度見る条件を必ず書く（〈見送りの台帳〉）。今の決まりに反するだけの案は、理由に、変える決まりと、変えれば入る形を書く。変える価値が大きいと見たら、大きな決めごととして利用者に聞く。
- **小さな決め**：主担当が決めて、理由を計画書の「決めごと」か HANDOFF.md の §4 に一行（案の箱分けは、案の一覧の判定の表）。
- **大きな決め**（〈大きな決めごとの一覧〉）：止まって利用者に聞く。書き方は「困ったこと・案・おすすめ」。おすすめは一つ。質問は三つまで。
- **相談役を使うとき**：段階③ は CLAUDE.md の「相談の手続き」、段階①-2・②-1・②-2 は関わり方（§3）。段階③ で相談が終わったら、結論を HANDOFF.md の §4.2 に写してから確認の一文で聞き、「はい」を待ってから次の行程に進む。
- 票や点数で決めない。利用者の答えは、日付つきで HANDOFF.md §4 に写す。

## 6. 仕事を分ける

| 役割 | 何をする | 何をしない |
|---|---|---|
| 主担当 | 考察・分析・統合・問いの立て直し・自分の案（段階①-2・②-1・②-2）、計画・設計・判断・仕様・差分の確認・確かめ・利用者への説明。〈重い層〉 を書く | — |
| 実装担当 | 段階③：仕様が決まった小さな実装。段階①-2：文書の機械的な直し | 仕様に無い判断、〈重い層〉、保存の形の変更、git の操作 |
| 調査担当 | ワークフローの中で、読んで集める | 編集、判定 |
| 検討担当 | 段階①-2・②-1・②-2 のワークフローの中で、案を広げる・伸ばす・疑う（主担当の案も疑う）。考察の観点（consult.js の `form: 'analysis'`） | 編集、判定、決定 |
| 相談役 | 段階③ は 〈合図の語〉 の論点、段階①-2・②-2 は関わり方 (B)(C)、段階②-1 は (B) のとき、(A) の始めの問いの立て直し。読み取り専用の相談 | 編集、決定、自分でのワークフロー起動 |

**実装担当に渡す大きさの目安**（超えるものは、仕様を分けるか、主担当が書く）：触るファイルは 1〜3、関心は一つ。非同期の流れ、面どうしのやりとりの型、保存の形は主担当が決めて書く。〈重い層〉 は触らせない。

仕様の形は docs/operating-kit/spec.template.md。仕様は `docs/wip/<日付>/specs/<名前>.md` に置き、「---」から下を渡す。返ってきた結果は、主担当が `git diff` を全部読み、改行が変わっていないかも見てから利用者に伝える。

## 7. 段階③ の流れ

1. 段階②-2 の計画書を読み、段を細かくする。計画が大きく違っていたら、段階②-2 へ戻ることを提案する。段階の外の小さな仕事は、計画書なしでよい。
2. 段ごとに作業枝の中で作る。
3. 段の仕様を書き、実装担当に頼む（§6）。
4. `git diff` を全部読む。〈型検査〉。必要なら画面の確かめ。
5. 〈重い層〉 を変えたら、ビルドを確かめたかを必ず書く。確かめた範囲と確かめていないことを分けて書く。
6. 段の終わりに、実装で分かった「前提の誤り」（計画や案が置いていた前提で、実際と違ったもの）を 〈思いつきの置き場〉 に一行ずつ書く（頭に「前提の誤り」、日付、段の名前、元の案の id があれば id）。次に段階②-1 で広げるときの材料になる。無ければ書かない。
7. 計画書の段の表を、実装の形に直す。HANDOFF.md を直す。
8. 作業枝にコミットし、`git fetch` してから push。PR は頼まれたときだけ。

## 8. 引き継ぎ（閉じるとき・主担当が替わるとき・段階を移るとき）

HANDOFF.md に書く（形は docs/operating-kit/HANDOFF.template.md）。長くしない。書くこと：今の段階（段階・関わり方・作業枝・案の一覧と考察ノートのパス・次の段階とその範囲）／今どうなっているか（HEAD、未コミットの変更、動いているもの）／次に何をするか（一つ。理由を一行）／利用者に聞くこと（おすすめ付き）／確かめたこと・確かめていないこと（分けて）／返事待ちの相談（止まるときに HANDOFF.md の §0 の 4 に一行。返事が来たら消す）。考えの手触り（捨てた筋、予感、利用者の答えでない言葉）は、HANDOFF.md ではなく考察ノートに書く。

## 9. 書き方

- モデル名は CLAUDE.md だけに書く。ほかの文書とコミットは、段階の名前と役割名。関わり方は記号 (A)(B)(C)・なし で書く。
- 丸数字の段階には必ず「段階」を付ける。「段階②」とだけ書くときは、段階②-1 と ②-2 の両方を指す。計画書の中の小分けは「段」。
- 日付は絶対日付。行番号は「見た時点の行」と書く。
- 運用の決まりを変えたら、docs/operating-kit/ のひな形も同じコミットで合わせる。
