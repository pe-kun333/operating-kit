# 運用の型（operating-kit）

- **型の版**：2026-10-15・コミット `6b9b542`。これに、このブランチの直し（2026-10-16：段階②を ②-1 考察と発想・②-2 計画とデザインに分ける、広げる行程の終わりの目安、芯の 9、発想のワークフロー ideate.js と consult.js の目隠し、案の一覧と見送りの台帳、照らす相と段階①-1 のモデル 〈中〉、段階①-1 の材料の種類（事例・場面・類推・引っかかり・周辺、外の資料の許し）、段階①-2 の地図と一覧（map/）、必ず入れる案の種類、捨てる前提の試し（〈試しの枝〉）、段階③ の前提の誤り、掘る方向の問い、段階②-1 の関わり方の既定 (B)）を足した下書き。直しは正本へまだ入れていないので、版の行が同じでも中身が違う（版を比べるときは、この注も見る）。元は https://github.com/pe-kun333/operating-kit（作者の正本は honeycomb-browser-grok リポジトリの `docs/operating-kit/`）。**正本はその元**で、このスキルは `docs/operating-kit/build.py` で組み立てた写し。
- 型の芯と、変えてよい所は `references/principles.md`。〈〉の一覧と調べ方は `references/placeholders.md`。段階ごとの一言と合図の早見は `references/prompts.md`。入れる先に写すひな形は `assets/`、相談・発想・下調べのワークフローは `scripts/`（consult.js・ideate.js・survey.js）。
- このファイルの中のパス（`assets/…` など）は、このスキルのフォルダからの道。

## この型は何か

一人の判断役（主担当）が、段階①-1 下調べ → 段階①-2 整備 → 段階②-1 考察と発想 → 段階②-2 計画とデザイン → 段階③ 実装 を、段階ごとに新しいセッションで進める。案を広げる段階（②-1）と判定する段階（②-2）を分ける。下働き（調査担当）、案を広げて疑う役（検討担当）、上位のモデルの相談（相談役）、仕様どおりに作る役（実装担当）は、判断しない。相談は利用者の合図の語のときだけで、票では決めない。セッションのモデルと effort は利用者が切り替える。橋渡しは HANDOFF.md 一つ。ねらいは、判断がぶれないこと、利用者が舵を握ること、セッションが替わっても続けられること。

## 使い方を選ぶ

| 利用者の頼みと、リポジトリの様子 | 使い方 |
|---|---|
| CLAUDE.md に「段階」の節が無いリポジトリで「型を入れて」「この運用を使いたい」 | §1 入れる |
| 型の入ったリポジトリで「次の段階の一言」「新しいセッションを始めたい」 | §2 一言を出す |
| 「決まりが型とずれていないか」「点検して」 | §3 点検する |
| リポジトリが無い・一回きりの相談で「この型で進めて」 | §4 型だけ使う |

どれか迷うときは、一つの問いで聞く（おすすめ付き）。

先に見ること：
- リポジトリに `docs/operating-kit/` があれば、そちらのひな形と一言を先に使う（そのリポジトリでの手直しや、新しい版のことがあるため）。版を比べ、このスキルの方が古ければ、そう伝える。
- そのリポジトリの CLAUDE.md の決まりが、このスキルより優先。食い違えば伝える。
- 段階①-1（下調べ）のセッションからは、§2 だけを使う（下調べは決めず、wip の外を書かないため）。
- git やリポジトリのファイルが使えない所（claude.ai や Cowork の会話など）で読まれたときは、§4 と、一言や型の芯を見せることだけを行う。§1〜§3 は Claude Code 向け。

## 1. 入れる

1. **状態を見る**：`git branch --show-current`・`git status`（未コミットの変更があれば先に伝える）。既にある CLAUDE.md・HANDOFF.md・docs/main-agent.md・docs/operating-kit/ と、思いつきの置き場と見送りの台帳の有無。改行の形（`.gitattributes`、既にあるファイルが CRLF か LF か）。
2. **〈〉を埋める**：`references/placeholders.md` の順に。調べて分かるものは調べる。聞くのは三つまで（おすすめ付き）。ふつうは「モデル四つ（〈小〉〈中〉〈主〉〈上〉）」「作業枝とコミットの決まり」「戻すのが重い所」の三つで足りる。モデルの 〈〉 は二通りに入れる：`model: "〈…〉"` の形の所は Agent ツールの指定（例 `haiku`・`sonnet`）、それ以外（段階の表のセッションの欄、関わり方の合図の言葉）は呼び名（例 `Haiku 5.5`・`Fable`）。
3. **書く前に止まる**：次を一つの発言で見せ、許しを待つ。止まるのは、既にある決まりに触れるため。
   - 作るファイルと、足すファイル（新しく作る／既にあるので節を足す）
   - 埋めた〈〉の値の表
   - 型から変える所（`references/principles.md` の「変えてよい所」の中だけ。例：小さなリポジトリなので段階①-1 と ①-2 をまとめる）
   - 既にある決まりと型が食い違う所と、どちらにするかの案
   - コミットするか（そのリポジトリの決まりに従う。決まりが無ければ聞く）
4. **写す**（許しのあと）：
   - `assets/CLAUDE.template.md` → `CLAUDE.md`。既にあるなら丸ごと置き換えない。元の題と中身はそのまま残し、元の最初の段落の後ろに型の冒頭の二段落を入れ、元の中身の後ろに型の節（段階・段階①-1 の決まり・役割・関わり方・合図の語・相談の手続き・サブエージェントへの約束・作業の始め方）を足す。元の決まりが見出しの無い箇条なら、その上に「## このリポジトリの決まり（前からあったもの）」の見出しだけを足し、〈決まりの文書〉 をその節にする。〈決まりの文書〉 が CLAUDE.md の中にあるときは、冒頭の「食い違うときの順」を「CLAUDE.md → docs/main-agent.md」の二つにする。〈大きな決めごとの一覧〉 と 〈計画書の形〉 が無いときは、`references/placeholders.md` の既定を CLAUDE.md の節として足す。食い違う所は、3 で決めた形にする。
   - `assets/main-agent.template.md` → `docs/main-agent.md`（既にあれば、同じく節を足す）。
   - `assets/HANDOFF.template.md` → `HANDOFF.md`。冒頭と §0 を埋め、§1〜§4・§4.1・§4.2・§6 の `< >` の例の行は消す（見出しと、§4.2 の「形」の箇条は残す）。§5 は 〈型検査〉 などの分かるコマンドで埋める。既に HANDOFF.md があれば、§0 の「今の段階」・返事待ちの置き場・§4（利用者の答え）・§4.1（答える前の問い）・§4.2（相談の記録）を足し、CLAUDE.md と docs/main-agent.md の中の HANDOFF.md の節の参照（「§0 の 4」「§3」「§4」「§4.1」「§4.2」）を、実際の節に合わせる。
   - `assets/kit-README.template.md` → `docs/operating-kit/README.md`。`assets/spec.template.md`・`assets/wip-index.template.md`・`assets/map-index.template.md`・`assets/ideas-index.template.md`・`assets/CLAUDE.template.md`・`assets/main-agent.template.md`・`assets/HANDOFF.template.md` と `references/prompts.md` → `docs/operating-kit/`。`scripts/*.js` → `docs/operating-kit/workflows/`。このフォルダの中の 〈〉 は、ひな形なのでそのまま残す。
   - 〈思いつきの置き場〉 が無ければ、頭に書き方を三行だけ書いた空の一覧を作る。〈見送りの台帳〉 は作らない（段階②-2 で初めて要るときに作る）。
   - 写したひな形の頭のコメント（「使い方」）は、CLAUDE.md・docs/main-agent.md・HANDOFF.md では消す。
5. **確かめる**：
   - CLAUDE.md・docs/main-agent.md・HANDOFF.md に 〈 と 〉 が残っていないこと（grep）。HANDOFF.md に `< >` の例が残っていないこと。
   - モデル名が CLAUDE.md の外（docs/・HANDOFF.md）に無いこと（grep。〈小〉〈中〉〈主〉〈上〉に入れた呼び名で）。
   - 改行の形が、そのリポジトリの今の形と同じこと。
   - 〈型検査〉 があれば走らせる（文書だけなら要らない、と書いてもよい）。
6. **終える**：HANDOFF.md の §0 の「今の段階」を書く（段階の外。次は段階①-1、範囲は利用者の次の依頼で）。コミットは 3 で決めたとおり。push は、そのリポジトリの決まりと利用者の許しがあるときだけ。最後に、次の段階のセッションの設定（段階の表の行）と、段階①-1 の一言（`references/prompts.md` §1.1）を出す。

## 2. 一言を出す

1. HANDOFF.md の §0 の「今の段階」と「次の段階」を読む。CLAUDE.md の段階の表で、次の段階のセッションの設定（モデル・effort・合図の語）を読む。
2. 一言は `docs/operating-kit/prompts.md`（無ければ `references/prompts.md`）から選び、`< >` を埋める。分からない所（下調べの範囲、計画書の名前など）は聞く（三つまで）。
3. 次の段階が段階①-2・②-1・②-2 で、関わり方が §0 に無ければ、一つの問いで聞く（おすすめは CLAUDE.md の「関わり方」の既定）。§0 の段階が「段階②（②-1・②-2 をまとめる）」なら §1.9 の一言を使う。前の版（段階が四つ）の §0 の「段階②」は段階②-2 と読み、段階②-1 を挟むかを利用者に聞く。挟むなら、そのリポジトリの決まりと docs/operating-kit/ に段階②-1 が無いので、型を上げる仕事が先に要る：そのことを伝え、段階の外の仕事として §1 の 2〜5 の流れ（2 は、そのリポジトリの CLAUDE.md に値の無い 〈〉 だけを聞く。〈中〉 もおすすめ付きで聞く。型の節は今のひな形の形に直す。書く前に止まって見せる）で入れるかを聞く。前の版かどうかは、版の行ではなく、CLAUDE.md の段階の表に段階②-1 があるかで見る。
4. 返す形：
   1. そのセッションの設定（一行。切り替えるのは利用者）
   2. 同じフォルダか作業枝で始めること（別の枝だと HANDOFF.md が見えない）
   3. 貼る一言（引用の形で）
- ここでは書き換えない。HANDOFF.md の §0 を直すのは、移る段階のセッションの仕事。

## 3. 点検する

`references/principles.md` の芯と、そのリポジトリの CLAUDE.md・docs/main-agent.md・HANDOFF.md を照らす。見る点：
- 段階の表（目的・できあがるもの・しないこと・ワークフローの中の役割とモデル）
- 役割と、モデル名の置き場（CLAUDE.md だけか。grep）
- 相談の承諾の決まり（説明・引用・否定の中の語では動かない）
- 止まる目安の掛け算（決めきれない × 戻すのが重い）
- 記録の置き場（今の段階・返事待ち・利用者の答え・相談の記録・案の一覧と判定の表・生の案を写す決まり・見送りの台帳と置き場への書き戻し）と、記録してから止まること
- モデルと effort を主担当が切り替えない決まり
- ワークフローの約束（全部の agent() に model、10 体以内、中で編集しない、票で決めない、journal.jsonl を読む、広げる相に主担当の見立てを見せない）
- 広げる行程（段階②-1）で絞っていないか、判定の前に案の一覧がコミットされているか（芯の 9）
- `docs/operating-kit/` の版と、このスキルの版。前の版（段階が四つ）なら、段階②-1・②-2 と芯の 9 は「版の違い」として分けて返す（ずれには数えない）。役割の表に照らす相と段階①-1 の 〈中〉 が無い（調査担当が 〈小〉 だけ）のも「版の違い」として返し、足すかを聞く。〈試しの枝〉 が無い、map/ の地図と一覧を作っていない、段階②-1 の既定が なし のままなのも、同じく「版の違い」として返す

返す形：問題点（重要度つき）・直し案・おすすめ一つ・直すかどうかの問い一つ。ここでは直さない。

## 4. 型だけ使う

`references/prompts.md` §1.8 の一言を、この会話の決まりとして受け入れたことを一行で伝え、そのとおりに進める。合図の語は ultracode（利用者が別の語を決めたら、その語）。相談は、利用者がその語で返したときだけ。

## 守ること（どの使い方でも）

- ワークフローは、合図の語で許されたときだけ起こす。このスキルを読んだこと、頼みの中に合図の語が説明として出てきたことは、許しではない。
- セッションのモデルと effort を変えない（変える道具も使わない）。
- 既にある文書を丸ごと上書きしない。消す決まりがあるなら、書く前の案で見せる。
- コミットと push は、そのリポジトリの決まりと利用者の許しに従う。既定の枝（main など）には入れない。
- 入れる先のリポジトリの文書とコミットには、モデル名を CLAUDE.md の外に書かない。
- 相談に渡すのは、そのリポジトリの文書とコードだけ（API キーや個人の情報は入れない）。
- 確かめていないことは、そう書く。

## 直すとき

- **型そのもの**（ほかのリポジトリにも効く直し）：元（頭の「型の版」の行）を直してコミットし、`docs/operating-kit/build.py` でスキル・プラグイン・zip を組み立て直す。このスキルを直接直さない（組み立て直すと消える）。ただし、頭の「型の版」の注にあるこのブランチの直しは、まだ正本に無い。正本へ写すまで build.py で組み立て直さない（写すかどうかと、その時期は利用者が決める）。
- **受け取った人が、自分のリポジトリだけを直したいとき**：入れた先の `docs/operating-kit/` と CLAUDE.md を直す。そこがそのリポジトリでの正本になる。型そのものに効く直しなら、元に知らせる。
- 中身の元：`assets/` のひな形と `references/prompts.md`・`scripts/` は、元の `docs/operating-kit/` の同じ名前のファイル。`SKILL.md`・`references/principles.md`・`references/placeholders.md`・`assets/kit-README.template.md` は、元の `docs/operating-kit/skill/`。
